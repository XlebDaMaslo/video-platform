# Отчёт по проекту

## Тема проекта

**Создание тестовой видеоплатформы с использованием технологий Python для бэкенда, React JS для фронтенда и Figma для дизайна**

## Цель работы

Целью проекта являлась разработка функционального веб-приложения для потокового видео, позволяющего пользователям регистрироваться, авторизоваться, загружать видеоконтент, просматривать видео и взаимодействовать с ним через комментарии. Также требовалось продемонстрировать применение современного стека веб-разработки и принципов UI/UX-проектирования.

## Используемые технологии

### Backend
- **Python 3.11** — основной язык серверной разработки.
- **Django 4.2** — фреймворк для построения серверной логики.
- **Django REST Framework** — реализация REST API.
- **Simple JWT** — аутентификация на основе JSON Web Token.
- **PostgreSQL** — хранение пользователей, видео и метаданных.
- **drf-spectacular** — генерация OpenAPI-схемы и Swagger UI.

### Frontend
- **React 18** — построение клиентского интерфейса.
- **Vite** — быстрый dev-сервер и сборщик проекта.
- **React Router** — маршрутизация между страницами.
- **React Query** — получение и кэширование данных с сервера.
- **Axios** — HTTP-клиент для взаимодействия с API.
- **React Hook Form** — обработка форм авторизации, регистрации и загрузки.
- **React Player** — встроенное воспроизведение видео.

### Дизайн
В качестве ориентира использовался предоставленный дизайн-макет в Figma. На его основе были выделены следующие принципы реализации интерфейса:
- тёмная тема с контрастным акцентным цветом;
- карточная структура отображения видеоконтента;
- минималистичная навигационная панель;
- разделение экранов на каталог, просмотр, профиль и загрузку.

## Архитектурный подход

При разработке проекта был применён подход разделения по слоям:

1. **Backend** отвечает за бизнес-логику, хранение данных и API.
2. **Frontend** реализует пользовательский интерфейс и взаимодействует с API.
3. **База данных** хранит постоянные сущности проекта.
4. **Документация** вынесена в отдельную директорию `docs/`, что улучшает сопровождение.

Бэкенд разделён на два независимых приложения:
- `users` — регистрация, вход, профиль;
- `videos` — видео, категории, комментарии и стриминг.

Такое разделение упрощает поддержку кода, повышает читаемость и соответствует принципам модульности.

## Реализованный функционал

### Функции бэкенда
- регистрация нового пользователя;
- авторизация и выдача JWT токенов;
- обновление access-токена;
- получение и изменение профиля;
- загрузка видео и обложки;
- список видео с поиском и фильтрацией;
- просмотр карточки видео;
- получение прямой ссылки для стриминга;
- добавление и чтение комментариев;
- список категорий.

### Функции фронтенда
- главная страница со списком видео;
- фильтрация и поиск;
- страница воспроизведения видео;
- форма входа;
- форма регистрации;
- страница загрузки видео;
- страница профиля;
- защита приватных маршрутов;
- автоматическое обновление JWT access-токена при 401-ошибке.

## Применённые подходы разработки

### 1. Модульность
Код разделён по назначению: модели, сериализаторы, представления, маршруты и тесты на бэкенде; страницы, компоненты, API-слой и стили на фронтенде.

### 2. DRY
Повторяющиеся части логики были вынесены в отдельные сущности. Например, единый `axiosInstance` автоматически добавляет токен авторизации ко всем запросам, а один хук `useAuth` инкапсулирует логику работы с токенами.

### 3. Принципы SOLID
- Каждая сущность имеет одну ответственность.
- Компоненты фронтенда не перегружены бизнес-логикой.
- API-слой изолирован от визуальных компонентов.
- Правила доступа к данным определены через отдельный permission-класс `IsOwnerOrReadOnly`.

### 4. Разделение API и UI
Интерфейс не зависит от серверной реализации напрямую: все данные получает через HTTP API. Это облегчает дальнейшее масштабирование и возможное подключение мобильного клиента.

## Трудности, возникшие в процессе разработки

### 1. Организация JWT-аутентификации
Основная трудность заключалась в корректной передаче токена в каждый защищённый запрос и в обработке ситуации, когда access-токен истёк.

**Решение:**
Был создан единый экземпляр Axios с interceptors. Перед каждым запросом он подставляет токен, а при ответе `401 Unauthorized` автоматически отправляет refresh-токен на эндпоинт обновления и повторяет исходный запрос.

### 2. Загрузка файлов и работа с `multipart/form-data`
При загрузке видео нужно было передавать не только текстовые поля, но и бинарные файлы (видео и обложку).

**Решение:**
На фронтенде использован `FormData`, а на бэкенде DRF автоматически обрабатывает multipart-запрос через сериализатор `VideoUploadSerializer`.

### 3. Разделение публичных и приватных действий
Не все действия должны требовать авторизацию. Например, просмотр видео и списка категорий должен быть публичным, а загрузка видео и написание комментариев — только для авторизованных пользователей.

**Решение:**
В представлениях были определены разные наборы permissions в зависимости от HTTP-метода.

### 4. Организация воспроизведения видео
В рамках тестового проекта требовалось реализовать потоковое воспроизведение без избыточного усложнения архитектуры.

**Решение:**
На первом этапе реализована выдача прямой ссылки на медиафайл через эндпоинт `/stream/`. Для реальной production-системы можно заменить этот механизм на HLS/DASH и вынести доставку в Nginx/CDN.

### 5. Структурирование проекта
При совмещении Django и React важно было организовать репозиторий так, чтобы фронтенд и бэкенд не мешали друг другу.

**Решение:**
Проект разбит на независимые каталоги `backend/` и `frontend/`, а общая сборка локальной среды выполняется через `docker-compose.yml`.

## Пути дальнейшего развития

В дальнейшем проект можно расширить следующими возможностями:
- лайки и подписки;
- плейлисты;

- CI/CD для автоматической проверки и развёртывания.
